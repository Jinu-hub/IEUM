### 주간 리포트: 프로젝트별 움직임 섹션 (`weekly-areas-v1`)

- 사용자: 태그·엔티티로 이슈를 요약하는 섹션을 추가. 단위는 project·component, 문장은 LLM. 입력은 highlight를 뺀 항목만(highlight는 이미 「今週の動き」가 요약함).
- 실측(11/02~11/08): 항목 143개 중 90개에 project·component·service 엔티티가 있으나, 같은 대상의 이름이 갈라져 있음(`MillviV3`·`Millvi V3`·`ミルビィV3`, `CLASSIC`·`CLASSICタスク`·`Classic`, `人事連携サービス`·`人事連携`). tagger가 자유 기입하고 project에는 ident가 없기 때문. 이름 그대로 코드로 묶으면 약 85개, 대부분 하루짜리라 섹션이 안 됨.
- 고른 방식: LLM이 대상(최대 6)을 정해 묶고 대상마다 1~2문장. 대상 이름은 인용한 항목의 엔티티 이름 중 하나를 그대로 써야 하고, 코드가 없는 id·중복 인용·없는 이름·입력에 없는 티켓 번호와 사람 이름을 거절. 모든 항목을 인용할 필요는 없음.
  - 안 고른 것: 이름 정규화 후 코드 묶기(가타카나·라틴 표기 차이를 못 합쳐 반만 해결), target별 project 목록으로 tagger 고정(근본 해결이지만 Core 쪽 변경·재생성 필요. 이름이 계속 흔들리면 그때).
- 입력은 topic·progress_roadmap. member_activity는 같은 내용이 사람 단위로 반복돼 뺌. `loadWeeklyInput`이 이 두 종류와 `entities_json`도 읽어 `core.others`에 둠(project·component·service 이름만). id는 `날짜/n`으로 highlight의 `날짜#n`과 구별.
- 렌더 위치: 「今週の動き」 다음, 클로징 앞. 제목 「🧩 プロジェクト別の動き」, 카드에 등장 날짜.
- 1회 실행(`gpt-6-sol`): 80항목 중 24개 인용, 6개 대상(2月案件, LEAD, ExtCalendarLinkTask, 管理者機能修正依頼表その7, 監督者ログ更新オプション, Millvi V3). 반려 1(한 항목을 두 대상에 넣음), 14초, $0.052. 출력 `works/out/weekly-report-p6`(머지 p3·Writer p5 재사용).
- 보인 점: Millvi V3·LEAD(ローソン移行)는 「今週の動き」와 주제가 겹침. `LEAD`는 팀 이름에 가까워 범위가 넓음. 같은 입력으로 다시 돌리면 뒤쪽 2개 대상이 바뀜(cs_content, コーポレート管理API).

### 주간 리포트: 프로젝트별 → 분류별 토픽 (`weekly-topics-v1`)

- 사용자: 프로젝트별이 아니라 샘플(`sample/merged.md` Topics Overview)처럼 Bugfix / Feature / Decision / Research 같은 일반 분류로 토픽을 보여주길 원함. 「プロジェクト別の動き」는 지움(`weekly-areas`와 `/weekly/areas` 삭제, migration v12 클래스를 `FlueWeeklyTopicsAgent`로. 배포 전이라 v12를 고침).
- 분류는 tagger의 `classifications_json.primary`(고정 8종). 11/02~11/08 topic·progress 80건 모두 값이 있음. 이름이 갈라지는 엔티티와 달리 코드가 정확히 묶음. 모델은 분류마다 1~2문장 + 근거 id 2~4개만.
- 매핑: bugfix→🐛 Bugfix, feature→🚀 Feature, coordination→📋 Decision, investigation→🔍 Research, 나머지(docs_spec·performance·tooling·release, 미분류)→🧰 Other. 건수는 코드가 셈. 샘플의 📈 Progress는 분류가 아니라 item 종류라 없음.
- 검사: 입력의 분류마다 정확히 한 문단, 근거 id는 그 분류 안에서만, 입력에 없는 티켓 번호·이름 거절.
