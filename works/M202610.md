- `generateContents`와 프롬프트, 템플릿, 분석·초안·리포트 프로세스를 작업 트리에서 제거. 결제 통화 타입, 샘플 요약, 기간 키 유틸은 유지.
- 이전 형식은 `docs/legacy-newsletter-generation.md`. 산출물 예시는 `sample/`. `output-sample`, `output-test`는 삭제.

- 소스 수집(`collect-sources.ts`)과 Flue 호출(`createContents`)을 나눔. 런 행은 `CRON_RECORD=0`이면 만들지 않음. 스킵·실패 시 `running`으로 남기지 않고 닫음.

- 배포 확인 Phase 1: Flue `/agents/*`에 Bearer 토큰(`FLUE_API_TOKEN`). 토큰 없음·틀림 401, 맞으면 202. `GET /`는 열림. 같은 값을 `flue/.dev.vars`와 루트 `.env`에 둠.

- 배포 확인 Phase 2: `https://ieum-flue.jinu30dev.workers.dev`에 배포. 시크릿 `OPENAI_API_KEY`, `FLUE_API_TOKEN` 등록. `GET /` 200, 토큰 없음·틀림 401. 배포용 Cloudflare 토큰은 "Edit Cloudflare Workers" 템플릿으로 새로 만듦(기존 `BROWSER-CONTROL`은 Browser Run 권한뿐이라 403).

- 배포 확인 Phase 3: 배포본에서 모델 호출 성공. 앱 `FLUE_AGENT_URL`을 배포 주소로 바꾸고 로컬 Flue(8787)를 끈 상태에서 즉시 발송. 21:06 메일 도착("D_G_S開発チーム Weekly Newsletter", 본문 파인애플 문장), Cloudflare 로그에도 같은 시각 요청이 error 없이 남음.
- 배포 확인 Phase 4: Worker에 `POST /db/ping`(토큰 필요) 추가. `fetch`로 Supabase REST에 `run_log_events` 한 줄 씀(201). 런 `e23d1b9e…`에 `step_name = flue_ping` 행 확인. 시크릿 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` 등록. 시크릿은 올린 뒤 수십 초 지나야 반영됨. `/db/ping`은 확인용이라 실제 파이프라인이 Supabase에 쓰게 되면 지움.
- 배포 확인 Phase 5: 긴 답(에세이)을 시키고 3초 뒤 재배포로 끊음. 요청은 실패하지 않고 32초 만에 `completed`. Flue가 잘린 답(6,887자, 문장 중간)을 남기고 숨은 system 메시지 2개("stream was interrupted", "Continue from the durable partial…")를 넣은 뒤 다시 돌림. 그런데 모델이 이어 쓰지 않고 처음부터 다시 써서(7,071자), 최종 답이 "잘린 앞부분 + 새 전체" 두 조각이 됨. 같은 대화 ID로 다시 보내면 기록이 이어 붙고, 새 답이 앞 내용에 영향을 받음.
  - 앱이 답의 첫 텍스트 조각을 꺼내던 것을 마지막 조각으로 고침(`create-contents.tsx`). 첫 조각은 잘린 앞부분일 수 있음.
  - 설계 메모: 재시작이 나도 요청은 끝까지 감. 대신 끊긴 단계는 토큰을 두 배 가까이 쓰고, 결과에 잘린 조각이 섞일 수 있음. 단계별 결과는 짧게 끊고 Supabase에 저장, 답은 구조화 출력이나 마지막 조각으로 받기. 대화 ID는 실행마다 새로(이전 기록이 섞이지 않게).
- 루트 Vite, Vercel, React Router는 그대로 둠.

# 2026-10-08

Daily Core 테이블을 Flue 계획(Vercel 수집 → Supabase 저장 → Cron → Cloudflare Worker가 Core 생성)에 맞춤.

## 한 일

- 기존 문서(`01`~`03`)와 `schema.ts`를 Flue 계획과 대조. 어긋난 곳은 넷: 수집 데이터를 둘 테이블이 없음, 파이프라인 단계를 나타낼 컬럼이 없음, 쓰지 않는 `job_queue`를 참조함, 모델·프롬프트가 필수라 대기열에 넣는 시점에 채울 수 없음.
- migration `0043` 생성·적용. 바뀐 테이블은 모두 0행이었음.
  - 새 테이블 `daily_core_source_data`: Daily Core × 소스 × 수집 1회당 한 행. 정규화본(`normalized_json`)만 저장하고 Provider 원본은 저장 안 함. 재수집은 덮어쓰지 않고 새 행 추가.
  - `daily_core_data`: `last_job_id` 삭제. `collection_stage`(pending / collected / failed)와 `collected_at` 추가. Cron은 `collected`인 날을 골라 Worker에 넘김.
  - `daily_core_generations`: `job_id` 삭제. `input_source_data_ids`(사용한 수집 행), `agent_conversation_id`(Flue 대화 ID), `agent_output_json`(병합 전 에이전트 출력) 추가. 모델·프롬프트·`started_at`은 선택값으로.
  - `daily_core_source_snapshots` 삭제.
- `db/queries.ts`, `db/mutations.ts`를 새 구조에 맞춤. 수집 행 저장은 `insertDailyCoreSourceData`(추가만 함).
- 문서 `02-daily-core-db-schema.md` 갱신(`job_queue` 섹션 → Flue로 실행 관리). `03`의 저장 트랜잭션 단계에서 snapshot 테이블 제거.
- `db:typegen` 실패. Supabase CLI가 IEUM 프로젝트(`jvdgefmtyduycwjdmfui`)가 없는 계정으로 로그인돼 있었음(보이는 프로젝트는 `supaTemp`, `MarketMemory`뿐). 실패하면서 `database.types.ts`를 0바이트로 덮어써서, 복원한 뒤 Daily Core 부분을 직접 고침. FK 이름은 실제 DB와 대조함.
